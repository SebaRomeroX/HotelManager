================================================================
1. GUIDANCE
================================================================

Non-negotiable constraints. Every later decision must respect these.

1.1 Minimalistic UI
- Plain, quiet, functional. Whitespace over decoration.
- No gradients, no shadows, no icon fonts, no animation beyond what
  immediate feedback requires.
- One accent colour. Hierarchy through spacing and type weight, not colour.

1.2 Mobile first
- Designed at 360px wide first; larger screens are progressive enhancement
  via min-width media queries only.
- Tap targets >= 44px, primary actions in the thumb zone.
- No hover-only affordances, no fixed-width layouts, no horizontal scroll.

1.3 Dark theme only, for now
- Single hard-coded dark palette. No light mode, no toggle, no
  prefers-color-scheme branching. Colours live in CSS custom properties
  so a second theme is a token swap later, not a rewrite.

1.4 Minimum dependencies
- Target: 0 runtime dependencies.
- Vanilla HTML + CSS + JavaScript. No framework, no bundler, no CSS
  framework, no runtime CDN, no icon library, no date library.
- Dev-time tooling only if genuinely unavoidable, and never required to
  run the app.

1.5 Front-end only, for now
- No server, no API, no auth, no database, no network calls at runtime.
- Everything executes in the browser and works offline.

1.6 localStorage for persistence
- All state persisted through one small storage module.
- No other code touches localStorage directly.
- Storage carries a schema version so migrations stay possible.

1.7 Conventions
- Plain ES modules, no build step. Small files, one responsibility each.
- Comments explain why, never what.
- Changes are small; anything non-obvious gets a dev log entry.


================================================================
2. PROJECT SPECIFICATION
================================================================

2.1 What this is
A single-user, browser-only hotel management app for day-to-day front
desk operations on a small property. It replaces a paper/whiteboard
workflow.

2.2 Users and scope
- One user (owner / front desk) on one device and one browser.
- No accounts, no roles, no multi-user sync, no multi-property support.
- Data lives only in that browser's localStorage.

2.3 Feature areas
Kept deliberately coarse. Details are decided feature by feature as we
build, and recorded in the dev log.
- Rooms: create and edit rooms.
- Room states: the operational status of a room.
- Reservations: guests staying in rooms over dates, plus the month calendar
  that ties rooms and reservations together.

Nothing else is in scope until these three are working.

2.4 Out of scope (for now)
- Accounts, auth, permissions, multi-user, server sync.
- Payments, invoicing, tax, receipts, printing.
- OTA / channel manager integrations, email, SMS.
- Light theme, i18n, multi-language, multi-property.

2.5 Tech baseline
- Static files only: HTML, CSS, ES modules.
- ES modules require a local HTTP server during development
  (file:// blocks module imports). `python3 -m http.server` is enough.
- No build, no transpile, no minify step. What is written is what ships.

2.6 File layout
  index.html            shell and semantic markup, no inline logic
  css/tokens.css        palette, spacing, type scale — the theme swap point
  css/app.css           layout and components
  js/app.js             bootstrap and view switching
  js/store.js           state container, persistence, migrations and status
  js/download.js        dated file download helper
  js/views/*.js         one module per screen
  js/components/*.js    small reusable render helpers
  tests/domain.test.mjs dependency-free domain checks (node:test)
  tests/store.test.mjs  storage, export and restore checks (node:test)
  tests/flows.mjs       optional Playwright browser flow checks
  package.json          dev commands only; no dependencies
  README.md             quick start, data model, tests and limitations
  roadmap.txt           this file

  Folders appear as they are needed, not in advance.

2.7 Design direction
- System font stack, no webfonts.
- Dark neutrals for background and surfaces, one accent for the single
  most important action on a screen.
- Spacing on a 4px scale; type limited to a few sizes.

2026-11-02  Occupancy time tracking: setting occupied asks for days, the card
            label counts down (OCCUPIED - 3 DAYS), and expiry flips the room to

            why: days turn over at 10:00 rather than midnight, so only the
            arrival date counts — arriving at 08:00 must not burn a day at 10:00
            two hours later, and the stay ends at 10:00 on arrival + N. The
            expiry is derived from stayStartedAt and stayDays instead of stored,
            so two copies of one deadline cannot drift across a DST change or a
            clock edit. Nothing can run in the background, so a stay that expires
            while the app is closed flips on the next load: the ticker reconciles
            at import, on focus, every minute, and precisely at the boundary.
            Any state other than occupied clears the stay fields so a stale
            countdown cannot resurface.

2026-11-02  Cleaning rooms count down 60 → 50 → … → 10 minutes and turn vacant
            at the hour; reconcileOccupancies renamed reconcileExpiries
            why: the label uses ceil(remaining / 10 min) so it changes exactly at
            each step — floor would drop to 50 after five minutes. Cleaning steps
            are not wall-clock aligned (a room cleaned at 14:37 ticks at 14:47),
            so the ticker sleeps until the earliest interesting moment across all
            rooms rather than running one interval per room. Duration is a
            constant like DAY_BOUNDARY_HOUR; a room already cleaning when this
            shipped has no start time, so it shows a plain label and never flips —
            same policy as legacy occupied. setRoomState now keeps at most one
            timer live per room, so a stale countdown cannot resurface.

2026-11-02  Stays count from the previous night when check-in lands between
            00:00 and 03:59: 01:10 on the 2nd with 1 day now expires 10:00 on
            the 2nd, not the 3rd. Supersedes the "only the arrival date counts"
            wording in the occupancy entry above.
            why: a check-in recorded at 01:10 "last night" did not flip at the
            10:00 boundary its owner expected — the clock's date said the 2nd
            while the night it bought was the 1st's. Night-of was chosen over
            calendar-date with eyes open: a 01:10 + 1-day stay now ends that
            same morning, which is short, but the calendar rule was wrong for
            every small-hours arrival. Cutoff is NIGHT_OF_HOUR = 4, and the
            hour must be read before startOfDay zeroes it — that ordering is
            the whole rule.

2026-11-02  Dev note: python http.server sends no Cache-Control, so the browser
            heuristically caches modules — a stale js/app.js once hid the whole
            ticker (the countdown rendered, nothing ever flipped). Hard-reload
            after code changes while iterating.
            why: heuristic freshness is 10% of the file's age, so a rarely-touched
            entry script stays "fresh" for hours after it changes while files
            edited minutes ago revalidate — mixing a stale entry with fresh
            dependencies loses a feature silently, with no error anywhere.

6. GRADE REVIEW
================================================================

Current grade: 8 / 10 (2026-11-13)
Target grade: 9 / 10

6.1 Why this is already better than a toy
- The scope is honest: three feature areas, no accounts, no network, no
  build step, no runtime dependency. The implementation matches the spec.
- Domain logic is separated from the DOM. Availability, capacity, group
  check-in, no-show reconciliation and schema migration are pure functions
  that can be tested without a browser.
- Hard cases are handled rather than deferred: the 10:00 boundary, the
  00:00-03:59 night-of rule, cleaning and OOS timers, multi-room atomic
  check-in, greedy arrival assignment, one-way schema migrations, and room
  deletion that refuses to strand a pending booking.
- The mobile UI is deliberate: 360px first, 44px targets, native dialogs,
  stable six-row calendar, explicit focus return after dialogs.
- Comments explain why, and the dev log records the reasoning behind
  non-obvious calls. That is rare and it is worth real marks.

6.2 What keeps the grade at 8
- The test suite is young. It proves the domain, the main flows, storage
  recovery, backup validation and the accessibility checklist, but the
  wider responsive range (item 7) is still unverified.
- Backup is manual. Export/restore is a file the user must remember to make;
  there is no scheduled backup or sync. That is the honest scope for a
  browser-only app, but one browser profile is still a single copy.
- Accessibility is now verified in one browser at 360px: keyboard paging,
  focus return, live regions, contrast and 200% text have a pass/fail
  checklist. It is not a cross-browser or screen-reader audit.
- Several modules are now large (reservations.js ~1000 lines, the
  reservation and state dialogs ~700 and ~640). The responsibilities are
  still coherent, but navigation costs are rising.
