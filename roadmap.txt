================================================================
1. GUIDANCE
================================================================

Non-negotiable constraints. Every later decision must respect these.

1.1 Minimalistic UI
- Plain, quiet, functional. Whitespace over decoration.
- No gradients, no shadows, no icon fonts, no animation beyond what
  immediate feedback requires.
- One accent colour. Hierarchy through spacing and type weight, not colour.

1.2 Mobile first
- Designed at 360px wide first; larger screens are progressive enhancement
  via min-width media queries only.
- Tap targets >= 44px, primary actions in the thumb zone.
- No hover-only affordances, no fixed-width layouts, no horizontal scroll.

1.3 Dark theme only, for now
- Single hard-coded dark palette. No light mode, no toggle, no
  prefers-color-scheme branching. Colours live in CSS custom properties
  so a second theme is a token swap later, not a rewrite.

1.4 Minimum dependencies
- Target: 0 runtime dependencies.
- Vanilla HTML + CSS + JavaScript. No framework, no bundler, no CSS
  framework, no runtime CDN, no icon library, no date library.
- Dev-time tooling only if genuinely unavoidable, and never required to
  run the app.

1.5 Front-end only, for now
- No server, no API, no auth, no database, no network calls at runtime.
- Everything executes in the browser and works offline.

1.6 localStorage for persistence
- All state persisted through one small storage module.
- No other code touches localStorage directly.
- Storage carries a schema version so migrations stay possible.

1.7 Conventions
- Plain ES modules, no build step. Small files, one responsibility each.
- Comments explain why, never what.
- Changes are small; anything non-obvious gets a dev log entry.


================================================================
2. PROJECT SPECIFICATION
================================================================

2.1 What this is
A single-user, browser-only hotel management app for day-to-day front
desk operations on a small property. It replaces a paper/whiteboard
workflow.

2.2 Users and scope
- One user (owner / front desk) on one device and one browser.
- No accounts, no roles, no multi-user sync, no multi-property support.
- Data lives only in that browser's localStorage.

2.3 Feature areas
Kept deliberately coarse. Details are decided feature by feature as we
build, and recorded in the dev log.
- Rooms: create and edit rooms.
- Room states: the operational status of a room.
- Reservations: guests staying in rooms over dates.
- Calendar: the timeline view tying rooms and reservations together.

Nothing else is in scope until these four are working.

2.4 Out of scope (for now)
- Accounts, auth, permissions, multi-user, server sync.
- Payments, invoicing, tax, receipts, printing.
- OTA / channel manager integrations, email, SMS.
- Light theme, i18n, multi-language, multi-property.

2.5 Tech baseline
- Static files only: HTML, CSS, ES modules.
- ES modules require a local HTTP server during development
  (file:// blocks module imports). `python3 -m http.server` is enough.
- No build, no transpile, no minify step. What is written is what ships.

2.6 File layout
  index.html            shell and semantic markup, no inline logic
  css/tokens.css        palette, spacing, type scale — the theme swap point
  css/app.css           layout and components
  js/app.js             bootstrap and view switching
  js/store.js           state container and persistence
  js/views/*.js         one module per screen
  js/components/*.js    small reusable render helpers
  roadmap.txt           this file

  Folders appear as they are needed, not in advance.

2.7 Design direction
- System font stack, no webfonts.
- Dark neutrals for background and surfaces, one accent for the single
  most important action on a screen.
- Spacing on a 4px scale; type limited to a few sizes.

3. DEV LOG

Format per entry:

Newest entries at the bottom.

2026-10-31  Rooms: creation flow in a native <dialog>, form and chip list together
            why: focus trap, Esc-to-close, backdrop and top layer come free, so no
            dependency and no overlay code to maintain. The dialog is mounted on
            document.body because #view repaints on every store write and would
            otherwise close itself mid-entry. Room type has no default and Add stays
            disabled until one is picked, so every room is deliberately typed
            instead of silently defaulted.

2026-11-01  Dialog showed on load; chips reshaped into a stacked list
            why: an author display on <dialog> overrides the UA rule that hides
            it while closed, so flex now only applies via [open]. Chips were a
            wrapped pill cloud and unreadable past a handful of rooms; they are
            now full-width rows with the type on the right.

2026-11-01  Chips are buttons; tapping one loads the room into the form as edit
            mode with Save, Cancel and a two-step Delete
            why: a span chip is unreachable by keyboard, so it became a real
            button. Edit state is transient UI rather than app data, so it lives
            in the component instead of the store. Delete arms itself on the
            first tap rather than calling confirm(), which blocks the page and
            cannot be styled.

2026-11-01  Rooms screen shows a two-up card grid; the room count line is gone
            why: the grid already shows how many rooms exist, so a number above
            it was noise. Cards are static because editing already has one home —
            the chip list inside Manage Rooms — and a second entry point would
            have to keep its own copy of the edit flow in sync.

2026-11-02  Room states: vacant, occupied, needs cleaning, cleaning, out of
            order; tapping a card opens a sheet to pick one. Schema bumped to 2
            so existing rooms gain a state.
            why: a popover anchored to a 158px card clips at 360px and needs
            flip-and-clamp code we would own forever, while a second <dialog>
            reuses the focus trap, Esc and backdrop already paid for in Manage
            Rooms. "Cleaning" replaced "In cleaning" so the state reads as "the
            room is cleaning", parallel to "occupied". Occupied is violet so it
            cannot collide with --accent, which owns buttons and the focus ring.
            Cards are interactive again, superseding the entry above: they now
            have a job.

2026-11-02  Rooms list in state order — vacant, cleaning, needs cleaning,
            occupied, out of order — with numeric-aware name sort inside each
            state; applies to both the card grid and the Manage Rooms chips
            why: ROOM_STATES became the single ranking, so the picker sheet
            reorders to match rather than carrying a second list that would
            drift. Sorting copies first because Array#sort mutates, and unknown
            states are ranked last because findIndex returns -1, which would
            otherwise float them to the top. numeric:true keeps "Room 10" after
            "Room 9" — a hotel passes nine rooms quickly.

2026-11-02  Occupancy time tracking: setting occupied asks for days, the card
            label counts down (OCCUPIED - 3 DAYS), and expiry flips the room to
            needs cleaning. New js/ticker.js drives the boundary.
            why: days turn over at 10:00 rather than midnight, so only the
            arrival date counts — arriving at 08:00 must not burn a day at 10:00
            two hours later, and the stay ends at 10:00 on arrival + N. The
            expiry is derived from stayStartedAt and stayDays instead of stored,
            so two copies of one deadline cannot drift across a DST change or a
            clock edit. Nothing can run in the background, so a stay that expires
            while the app is closed flips on the next load: the ticker reconciles
            at import, on focus, every minute, and precisely at the boundary.
            Any state other than occupied clears the stay fields so a stale
            countdown cannot resurface.

2026-11-02  Cleaning rooms count down 60 → 50 → … → 10 minutes and turn vacant
            at the hour; reconcileOccupancies renamed reconcileExpiries
            why: the label uses ceil(remaining / 10 min) so it changes exactly at
            each step — floor would drop to 50 after five minutes. Cleaning steps
            are not wall-clock aligned (a room cleaned at 14:37 ticks at 14:47),
            so the ticker sleeps until the earliest interesting moment across all
            rooms rather than running one interval per room. Duration is a
            constant like DAY_BOUNDARY_HOUR; a room already cleaning when this
            shipped has no start time, so it shows a plain label and never flips —
            same policy as legacy occupied. setRoomState now keeps at most one
            timer live per room, so a stale countdown cannot resurface.

2026-11-02  Stays count from the previous night when check-in lands between
            00:00 and 03:59: 01:10 on the 2nd with 1 day now expires 10:00 on
            the 2nd, not the 3rd. Supersedes the "only the arrival date counts"
            wording in the occupancy entry above.
            why: a check-in recorded at 01:10 "last night" did not flip at the
            10:00 boundary its owner expected — the clock's date said the 2nd
            while the night it bought was the 1st's. Night-of was chosen over
            calendar-date with eyes open: a 01:10 + 1-day stay now ends that
            same morning, which is short, but the calendar rule was wrong for
            every small-hours arrival. Cutoff is NIGHT_OF_HOUR = 4, and the
            hour must be read before startOfDay zeroes it — that ordering is
            the whole rule.

2026-11-02  Dev note: python http.server sends no Cache-Control, so the browser
            heuristically caches modules — a stale js/app.js once hid the whole
            ticker (the countdown rendered, nothing ever flipped). Hard-reload
            after code changes while iterating.
            why: heuristic freshness is 10% of the file's age, so a rarely-touched
            entry script stays "fresh" for hours after it changes while files
            edited minutes ago revalidate — mixing a stale entry with fresh
            dependencies loses a feature silently, with no error anywhere.

2026-11-03  Reservations: a New reservation button opens a modal form (room
            type, arrival date, duration, host name) and the screen lists
            bookings by proximity — upcoming soonest first, then the past with
            the most recent first. New js/reservations.js domain module and
            js/components/reservation-dialog.js; schema untouched because
            state.reservations already existed.
            why: a reservation books a night to come, so the date picker opens
            on today and validation refuses earlier ones — backfilled history
            belongs to the room itself, not to a booking. The checkout date is
            derived from arrival + duration and never stored, so the two halves
            of one range cannot drift apart (same rule as stay expiry). One
            reservationError() shared by the dialog and addReservation keeps
            the message the user reads and the write that gets refused from
            ever disagreeing. The sheet closes on save so the new row is
            visible immediately; saving repaints the view, so focus is restored
            to the New reservation button by hand — the opener element the
            browser would restore no longer exists by then.

2026-11-03  Tapping a reservation opens the same sheet in edit mode: the
            title and submit swap, the host name becomes a static "Host: …"
            hint, and a two-step Cancel reservation button (armed on first
            tap) removes the booking. Rows are now real buttons so they are
            keyboard-focusable like room cards.
            why: the host name is fixed at creation — who the booking belongs
            to is not desk-editable, so the field is replaced by text rather
            than left as a disabled input, which would still look like a
            field. A booking whose date has already passed keeps that date
            through an edit (only a changed date must be a night to come) —
            otherwise arriving would lock the record behind a validation
            error. updateReservation never writes hostName even if passed
            one, and unknown ids return the state unchanged, so a stale tap
            cannot corrupt anything. Focus returns to the edited row's
            button, falling back to New reservation after a cancel removes
            it — the repaint detached the opener the browser would restore.

2026-11-04  Reservations split into three sections — Today, Incoming, Past —
            and past bookings became read-only: tapping one opens the sheet
            with host and stay details as static text, no inputs, no save,
            only the two-step Cancel reservation. Supersedes yesterday's
            "unchanged past date OK" edit rule: the currentDate option is gone
            from reservationError because an editable booking can now only
            ever have an arrival date of today or later. The meta line moved
            into reservationMeta() so the row and the read-only sheet cannot
            print different ranges.
            why: isPastReservation draws the one past line — arrival before
            today — and both the section grouping and the edit lock go through
            it, so a row shown under Past can never be edited from under it.
            An unparseable date counts as past as well: a corrupt entry lands
            in the read-only section where it can still be cancelled instead
            of sitting in Incoming forever. updateReservation refuses past
            bookings outright, so even a stale tap or a sheet left open across
            midnight cannot rewrite history — while delete stays allowed,
            because removing a wrong record is not editing one.

2026-11-04  Today's reservations now hold a free room automatically: the rooms
            screen paints OCCUPIED - ARRIVING (accent border) on a vacant
            room of the booking's exact type, derived fresh on every render —
            nothing stored, so occupying or OOS-ing the held room moves the
            marker to the next free match by itself. Tapping the reservation
            offers Check in: one update takes the room into a real occupied
            stay (stayDays/stayStartedAt via setRoomState) and stamps
            checkedInAt on the booking. An unvalidated booking auto-cancels
            at 04:00 the next morning — NIGHT_OF_HOUR — and is removed like
            any manual cancel.
            why: 04:00 rather than midnight because that is exactly the
            night-of line the 01:10 arrivals need — a booking for the 5th
            stays check-in-able into the small hours of the 6th, so
            isPastReservation now means "arrival window closed" for pendings
            (00:00 D … 04:00 D+1) instead of "date < today"; sorting,
            grouping, the edit lock and the read-only sheet all read that one
            function, which is what keeps sections and lock in step — and
            restores the unchanged-date pass in reservationError, since a
            straddling booking legitimately edits with yesterday's date.
            A check-in booking is read-only afterwards: its duration lives
            on the room now and there is no propagation back yet (TODO). The
            ticker arms on midnight and on each cutoff alongside 10:00 and
            cleaning steps, so sections roll and no-shows expire exactly on
            time instead of at the next stray repaint.

2026-11-04  Fix: tapping a state in the room-state sheet no longer throws —
            picking a state now applies it and closes the sheet. render() read
            `roomId`, a name that only exists as a local inside the row click
            handler, so every store write died on a ReferenceError.
            why: the failure order is what made it look like a save bug —
            the store persists BEFORE notifying listeners, so the state change
            was already on disk (hence "refresh and you'll see it") while the
            throw unwound commit() before dialog.close(), leaving the modal
            open over a half-repainted view. Fixed to activeRoomId. Notably
            invisible to our static battery: node --check and the
            import-resolution pass both accept undefined identifiers — the new
            Playwright smoke suite (/tmp/opencode/smoke/smoke.mjs, Chromium
            against a local server) is what catches this class: it failed with
            "ReferenceError: roomId is not defined" against the old code and
            passes clean now, covering state changes, the days form, the
            arriving hold, check-in and read-only sheets end to end.

2026-11-04  Availability guards: a reservation now keeps a room. The days
            form runs occupancyConflict before committing — simulate the stay,
            then for every booking the room can no longer serve ask whether
            some other room of the type still can. In-window bookings need a
            VACANT room (that is what the OCCUPIED - ARRIVING hold is), future
            ones need a stay ending by their line; nothing left → refused,
            same reference, with "That stay overlaps Ana's arrival on Nov 5."
            Check-in runs the same conflict excepting itself, so a guest at
            the desk can never silently strand another booking. Add/edit
            gained reservationAvailabilityError — "No Suite room is free on
            Nov 5." on the roomType field — but only when type or date moves:
            a duration tweak never sees it, and a record that was impossible
            before this guard existed stays editable.
            why: the line is 10:00 on the arrival day because that is the
            checkout hour — back-to-back stays (A out at 10:00, B in the same
            day) must remain bookable, while a room still occupied past that
            morning leaves the arriving host nothing to check into. In-window
            bookings are counted rather than matched: one vacant room short
            and the booking last in line (soonest arrival, then name) is the
            one named — exactly the one arrivingAssignment would strand.
            Scope decision: only set-occupied is guarded — OOS, dirty and
            cleaning stay the desk's freedom, so they can still move a live
            hold (accepted for now, see TODOs). The booking guard reads rooms
            against the date, not against other bookings: two bookings
            competing for the only room still both get added and surface as
            "No free room" at check-in (also a TODO). Found on the way by the
            smoke suite: the first reachable roomType error blew up because
            form.elements.roomType is a RadioNodeList — no setAttribute or
            focus of its own — so setError and the submit focus now unwrap
            radio groups to their individual inputs.

2026-11-05  Calendar: the placeholder view is now a month grid. Each cell
            shows one number — how many rooms could still be sold that night
            — from availabilityOn(state, iso): per type, rooms not out of
            order and not held by a live stay, minus the nights
            not-checked-in bookings cover, clamped at 0 (old overbooked data
            can never read -1), summed across types. Monday-first week; past
            days dimmed but keep their counts, today wears an accent ring,
            a sold-out night prints its 0 in red (past 0s stay dimmed — red
            is for nights that can still hurt). Tap a day → bottom sheet
            with the per-type breakdown ("Small · 1 of 2 free") and a New
            reservation button that opens the booking sheet with that date
            prefilled; the button is hidden once the night is behind us.
            Month state is module-level: null means "follow today", arrows
            set {year, month}, Today resets to null — so a repaint after a
            state write never yanks a browsed month back to the live one,
            and Today only appears once you have browsed away. Nav repaints
            via section.replaceWith(render()) and refocuses the arrow used,
            because app.js's render is not reachable from a view and losing
            focus every arrow press would strand keyboard users.
            why: the cell answers the only question the desk asks — "a
            guest wants this date, how many can I still sell?" — so it
            reuses the exact guard line the booking guards use rather than
            inventing a second definition of free. One subtlety: it cannot
            be raw roomServes. roomServes is written for arrivals of today
            or later — a stay that began yesterday would fail its end check
            for every night last week and paint the whole past red. So
            stayCoversNight checks both sides of the stay: it inverts
            stayExpiry to recover the arrival day (no second copy of the
            night-of rule to drift) and covers [arrivalDay, checkoutDay) —
            the checkout morning frees the room for that night, same as
            back-to-back. Checked-in records are skipped entirely: their
            room's live stay already accounts them, and counting both would
            subtract the same guest twice. A booking covers [arrival,
            arrival + days); dirty and cleaning rooms count as sellable
            (turnover is assumed, exactly like roomServes). The detail
            sheet subscribes to the store so a tick flipping a room while
            it is open keeps the breakdown honest, and on close focus
            returns to the cell — re-queried by date, because a repaint
            while the sheet was open makes the original element stale.
